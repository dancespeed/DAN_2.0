Отличная идея. Чекпоинты как раз не дают архитектуре "расползаться". Зафиксируем текущее состояние DAN 2.0.

---

# DAN 2.0 — Checkpoint №1

## Статус: Архитектурный фундамент

### 1. Структура проекта (утверждена)

```text
src/
│
├── core/
├── platform/
└── modules/
```

Изменению не подлежит без пересмотра архитектуры.

---

## 2. Ответственность каталогов

### core

Ядро платформы.

* жизненный цикл;
* транспорт;
* сообщения;
* конфигурация;
* маршрутизация.

---

### platform

Аппаратно-зависимый слой.

* GPIO
* I2C
* SPI
* UART
* CAN
* EEPROM
* Flash
* Timers
* ...

Не содержит логики платформы.

---

### modules

Функциональные модули.

* Input
* PWM
* Logic
* Storage
* Display
* ...

---

# 3. Пространства имён

Архитектура определяется namespace.

```cpp
namespace dan
{
    namespace core {}
    namespace platform {}
    namespace modules {}
}
```

---

# 4. Правило классов

Класс создаётся только тогда, когда объект имеет:

* состояние;
* ответственность;
* жизненный цикл.

Namespace используется только для организации кода.

---

# 5. System

Главный объект платформы.

Публичный интерфейс:

```cpp
Initialize()
Start()
Run()
Stop()
```

Ответственность:

* владение ядром;
* жизненный цикл;
* запуск;
* остановка.

---

# 7. Две таблицы системы

## ConfigurationTable

Постоянное описание устройства.

Используется только при загрузке.

Содержит:

* что существует;
* параметры;
* описание объектов.

---

## ModuleTable

Рабочая таблица маршрутизации.

Содержит только успешно инициализированные адресаты.

После загрузки:

```text
Register()
    ↓
Seal()
```

становится неизменяемой.

---

# 8. Загрузка системы

```text
ConfigurationTable
        │
        ▼
System
        │
        ▼
INIT через MessageBus
        │
        ▼
ModuleTable.Register()
        │
        ▼
Seal()
        │
        ▼
Run()
```

После перехода в `Run()` конфигурация больше не участвует в маршрутизации.

---

# 9. Основной принцип DAN 2.0

> **Во время загрузки система преобразует описание устройства (`ConfigurationTable`) в рабочую карту маршрутизации (`ModuleTable`). После перехода в рабочий режим используется только `ModuleTable`.**

---

## Следующий кирпичик

Считаю логичным перейти к проектированию **`ConfigurationTable`**.

Не к реализации, а именно к её архитектуре:

* формат записи;
* структура ID;
* описание объекта;
* минимальный набор полей.

Это будет первый настоящий компонент ядра, от которого затем будут строиться `Message`, `MessageBus` и `ModuleTable`.
