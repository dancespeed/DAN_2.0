Я понял устройство DAN как **одноузловую встроенную систему с единым жизненным циклом и внутренним сообщенческим протоколом**, где модули не должны напрямую управлять друг другом.

При этом важно разделить уже утверждённое, текущее состояние кода и ещё не спроектированные части.

# 1. Общая структура устройства

Верхний уровень:

```text
main
 └── System
      ├── Platform
      └── Runtime
```

## `Platform`

Отвечает за аппаратную основу конкретного контроллера:

* прерывания;
* системный таймер;
* аппаратные периферийные службы;
* диагностику платформы;
* в дальнейшем — CAN, EEPROM, UART и другие аппаратные компоненты.

В текущем архиве `Platform` уже управляет:

```text
Interrupt
SystemClock
Heartbeat
```

## `Runtime`

Отвечает за программную среду DAN:

* регистрацию модулей;
* их инициализацию;
* запуск;
* циклическое выполнение;
* остановку;
* в дальнейшем — объекты, внутреннюю шину и маршрутизацию сообщений.

Текущая структура:

```text
Runtime
 └── ModuleTable
      └── Module
```

# 2. Порядок запуска устройства

## Вход из Arduino Framework

```cpp
void setup()
{
    System::Initialize();
    System::Start();
}

void loop()
{
    System::Run();
}
```

Таким образом:

* `setup()` выполняет подготовку и запуск;
* `loop()` непрерывно вызывает рабочий цикл;
* `Stop()` предусмотрен архитектурой, хотя в обычном Arduino-цикле пока явно не вызывается.

---

## Этап `Initialize`

```text
System::Initialize()
    │
    ├── Platform::Initialize()
    │     ├── запрещение прерываний
    │     ├── настройка системного таймера
    │     └── настройка heartbeat
    │
    └── Runtime::Initialize()
          ├── ModuleTable::Initialize()
          ├── RegisterModules()
          └── ModuleTable::InitializeModules()
```

Сначала готовится аппаратная основа, затем программные модули.

Очень важный принцип:

```text
Сначала зарегистрировать все модули
Только затем инициализировать их
```

Это означает, что во время `OnInitialize()` модульная структура уже полностью известна.

---

## Этап `Start`

```text
System::Start()
    │
    ├── Platform::Start()
    │     ├── запуск системного таймера
    │     └── разрешение глобальных прерываний
    │
    └── Runtime::Start()
          └── ModuleTable::Start()
                └── Module::Start()
```

Сначала запускается аппаратная среда, затем программная.

Модуль может перейти в рабочее состояние только так:

```text
Stopped
   ↓ OnInitialize() == true
Initialized
   ↓ OnStart() == true
Running
```

Переходами управляет базовый класс `Module`, а не конкретный модуль.

---

## Этап `Run`

Каждая итерация главного цикла:

```text
System::Run()
    │
    ├── Platform::Run()
    │     ├── чтение системного времени
    │     └── обновление heartbeat
    │
    └── Runtime::Run()
          └── ModuleTable::Run()
                └── OnRun() каждого Running-модуля
```

На данном этапе это кооперативная модель:

* нет отдельного потока для каждого модуля;
* модули последовательно получают короткий вызов `OnRun()`;
* модуль не должен надолго блокировать главный цикл.

В дальнейшем внутри этого цикла должен обслуживаться и внутренний транспорт сообщений.

---

## Этап `Stop`

Порядок симметричен запуску, но обратный:

```text
System::Stop()
    │
    ├── Runtime::Stop()
    │     └── модули останавливаются
    │         в обратном порядке регистрации
    │
    └── Platform::Stop()
          ├── запрет прерываний
          ├── остановка heartbeat
          └── остановка системного таймера
```

То есть программные потребители останавливаются до аппаратной основы.

Это правильная зависимостная модель:

```text
При запуске:    Platform → Runtime
При остановке:  Runtime  → Platform
```

---

# 3. Как я понимаю внутреннюю шину

Внутренняя шина DAN — это не физическая CAN-шина и не прямой вызов функций.

Это программный транспорт:

```text
Producer
    ↓
Message
    ↓
MessageBus
    ↓
маршрутизация
    ↓
Object / Module
```

Основной принцип:

> Модули не должны вызывать друг друга напрямую. Взаимодействие и конфигурация проходят через сообщения DAN.

Например, нежелательная связь:

```cpp
inputModule.SetPwm(...);
```

Предполагаемая связь DAN:

```text
InputModule
    ↓ публикует Message
MessageBus
    ↓ доставляет
объект PWM
```

Это снижает связанность модулей и позволяет заменять, добавлять или отключать их без формирования сети прямых зависимостей.

---

# 4. Структура сообщения внутренней шины

Зафиксированный размер:

```text
8 байт
```

Общая структура:

```text
┌──────────────────────────────┐
│ Header             32 бита   │
├──────────────────────────────┤
│ ObjectId           16 бит    │
├──────────────────────────────┤
│ Value              16 бит    │
└──────────────────────────────┘
```

В ранее зафиксированной декомпозиции заголовок имеет вид:

```text
Header, 32 бита
├── Sender             8 бит
├── Receiver           8 бит
├── MessageType        2 бита
├── MessageAttribute   2 бита
└── MessageId         12 бит
```

Итого:

```text
8 + 8 + 2 + 2 + 12 = 32 бита
```

Полное сообщение:

```text
Header    4 байта
ObjectId  2 байта
Value     2 байта
────────────────
Всего     8 байт
```

# 5. Смысл полей сообщения

## `Sender`

Кто создал сообщение.

Это идентификатор исходного модуля:

```text
Input
Logic
System
CAN
и т. д.
```

Отправитель нужен для:

* диагностики;
* проверки прав;
* ответа;
* определения источника события.

---

## `Receiver`

Модуль, которому адресовано сообщение.

Зафиксированное пространство адресов предполагалось таким:

```text
0x00       недопустимый адрес
0x01–0xFE  реальные модули
0xFF       broadcast
```

При этом broadcast допустим как получатель, но не как отправитель.

В текущем коде `ModuleId` действительно имеет размер `uint8_t`. В последнем текстовом чекпоинте встречается `uint16_t`, но это не совпадает с фактическим архивом и с 8-битным полем заголовка. Поэтому источником истины сейчас считаю текущий код и утверждённую 8-битную адресацию модуля.

---

## `MessageType`

Определяет общий характер операции.

Точные значения для DAN 2.0 ещё необходимо сверить или заново утвердить. Концептуально это могут быть различия вроде:

```text
Command
Event
Request
Response
```

Но считать эти конкретные четыре значения окончательно утверждёнными пока нельзя.

---

## `MessageAttribute`

Дополнительная характеристика сообщения.

Для неё зарезервированы два бита внутри заголовка. Точное назначение всех комбинаций в текущем этапе ещё не утверждено.

То есть архитектурно поле есть, но его семантику нельзя придумывать до отдельного обсуждения.

---

## `MessageId`

Это семантический код операции:

```text
SET_PIN
SET_ACTIVE_LEVEL
SET_VALUE
INITIALIZE
READ
SAVE
и т. п.
```

`MessageId` объясняет, **что нужно сделать или что произошло**.

Он не должен быть локальным случайным номером конкретной прошивки. Это часть стабильного протокола DAN.

---

## `ObjectId`

Это адрес конкретного объекта внутри функционального пространства DAN.

Я понимаю разделение так:

```text
Receiver   → какой модуль должен принять сообщение
ObjectId   → к какому объекту внутри этого модуля относится сообщение
MessageId  → какая операция выполняется
Value      → передаваемое значение
```

Пример:

```text
Receiver  = PWM
ObjectId  = PWM channel 2 duty
MessageId = SET_VALUE
Value     = 750
```

Это означает не просто «отправить число модулю PWM», а:

> передать объекту коэффициента заполнения второго PWM-канала команду установки значения 750.

---

## `Value`

Это сырое 16-битное поле.

```text
uint16_t raw value
```

Само сообщение не хранит полную информацию о типе и единице измерения.

Интерпретация определяется описанием объекта:

* `Bool`;
* `UInt16`;
* `Int16`;
* масштаб;
* режим доступа.

Например:

```text
Value = 237
Scale = -1
```

означает:

```text
23.7
```

То есть шина остаётся компактной, а знания о смысле значения находятся в дескрипторе объекта.

---

# 6. Предполагаемая маршрутизация сообщения

На основании принятых решений я понимаю её следующим образом:

```text
1. Производитель формирует Message
2. Message передаётся в MessageBus
3. MessageBus помещает его во внутреннюю очередь
4. Транспорт извлекает сообщения в порядке FIFO
5. По Receiver определяется целевой модуль
6. По ObjectId определяется объект
7. Проверяются тип операции, доступ и значение
8. Сообщение передаётся обработчику объекта
9. Объект изменяет состояние или формирует ответное сообщение
```

Схематически:

```text
Message
  │
  ▼
MessageBus / Queue
  │
  ▼
Receiver
  │
  ▼
ModuleTable::Find(receiver)
  │
  ▼
ObjectTable::Find(objectId)
  │
  ▼
Object handler
```

Однако здесь есть важная граница.

## Что утверждено

Утверждены:

* восьмибайтный формат;
* адрес отправителя и получателя;
* `ObjectId`;
* `MessageId`;
* сырое 16-битное значение;
* конфигурация как последовательность сообщений;
* отсутствие прямых вызовов между модулями.

## Что ещё не утверждено в текущей DAN 2.0

Пока не завершено проектирование:

* `Object`;
* `ObjectTable`;
* точного владельца `ObjectTable`;
* интерфейса приёма сообщения модулем или объектом;
* внутренней очереди `MessageBus`;
* правил переполнения очереди;
* количества сообщений, обрабатываемых за один `Run()`;
* синхронной или строго асинхронной доставки;
* обработки broadcast;
* ошибок доставки;
* ответа на неизвестный `ObjectId`;
* окончательной семантики `MessageType` и `MessageAttribute`.

Старые чекпоинты содержат уже существовавшие реализации `MessageQueue`, `MessageBus` и `MessageDispatcher`, но я воспринимаю их как историю предыдущей архитектуры, а не как автоматически действующее решение для нового ядра DAN 2.0.

# 7. Конфигурация устройства проходит по той же шине

Это одно из наиболее важных решений.

`ConfigurationTable` не является набором C++-структур модулей. Она содержит готовые сообщения:

```cpp
struct ConfigurationTable
{
    uint16_t messageCount;
    Message messages[];
};
```

Последовательность загрузки я понимаю так:

```text
Flash
  │
  ▼
ConfigurationTable
  │
  ▼
System последовательно читает сообщения
  │
  ▼
MessageBus
  │
  ▼
целевые модули и объекты
```

Пример конфигурации входа:

```text
SET_PIN
SET_ACTIVE_LEVEL
SET_CLICK_MODE
INITIALIZE
```

Для модуля это обычные сообщения. Ему неважно, пришли они:

* из таблицы конфигурации;
* по CAN;
* от другого модуля;
* из диагностического интерфейса.

Это создаёт единый механизм управления.

---

# 8. Разница между конфигурацией и рабочим режимом

## Во время загрузки

```text
ConfigurationTable
    ↓
MessageBus
    ↓
создание и настройка рабочего состояния
```

## После запуска

```text
ConfigurationTable больше не участвует

Runtime
    ↓
MessageBus
    ↓
Modules / Objects
```

То есть конфигурационная таблица является сценарием старта, а не постоянно используемой базой маршрутизации.

# 9. Итоговая картина моего понимания

```text
                   ┌─────────────────────┐
                   │        System       │
                   └──────────┬──────────┘
                              │
             ┌────────────────┴────────────────┐
             │                                 │
             ▼                                 ▼
       ┌──────────┐                      ┌──────────┐
       │ Platform │                      │ Runtime  │
       └──────────┘                      └────┬─────┘
                                             │
                                      ┌──────▼──────┐
                                      │ ModuleTable │
                                      └──────┬──────┘
                                             │
                                          Modules
                                             │
                                          Objects
                                             ▲
                                             │
Producer → Message → MessageBus → routing ───┘
```

А логическая структура адресации сообщения:

```text
Sender
  │
  ├── кто отправил
  │
Receiver
  │
  ├── какой модуль принимает
  │
ObjectId
  │
  ├── какой объект выбран
  │
MessageId
  │
  ├── что нужно сделать
  │
Value
  │
  └── с каким значением
```

Главное архитектурное свойство DAN я вижу так:

> **Вся система управляется единообразными компактными сообщениями. Модули обеспечивают функциональность, объекты предоставляют адресуемые точки данных и действий, а внутренняя шина разрывает прямые зависимости между компонентами.**

Следующий кирпичик действительно должен уточнить модель `Object`: что именно является объектом, кому он принадлежит и какой минимальный интерфейс нужен ему для обработки сообщений.
