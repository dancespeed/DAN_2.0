# DAN 2.0 — Checkpoint №2

## Подсистема конфигурации

### Принцип

**Конфигурация — это сценарий загрузки системы.**

Она не описывает объекты в виде структур, а представляет собой последовательность сообщений DAN.

---

## Формат

```cpp
ConfigurationTable
{
    uint16_t messageCount;
    Message messages[];
};
```

где `Message` — это уже утверждённый внутренний протокол DAN размером 8 байт.

---

## Загрузка

```text
System
    │
    ▼
ConfigurationTable
    │
    ▼
for (0 … messageCount)
    │
    ▼
MessageBus.Send()
```

Никаких специальных загрузчиков.

Никаких конвертеров.

Никаких промежуточных структур.

---

## Получение

Каждый модуль получает конфигурацию так же, как и любые другие сообщения.

Например:

```
InputModule

SET_PIN
SET_ACTIVE_LEVEL
SET_CLICK_MODE
INITIALIZE
```

Это обычные сообщения DAN.

---

## После загрузки

После окончания обработки таблицы:

```
ConfigurationTable
        │
        └── больше не используется

ModuleTable
        │
        └── используется всю работу системы
```

# Что осталось спроектировать

На мой взгляд, мы подошли к самой интересной части проекта. Остались уже не общие идеи, а ядро транспорта.

Я бы предложил следующий порядок:

1. **ModuleId** — полный перечень системных модулей и правила их адресации.
2. **MessageId** — единая система идентификаторов сообщений (инициализация, команды, события, запросы и т.д.).
3. **MessageAttribute** — определить назначение 16 возможных значений (4 бита).
4. **ModuleTable** — окончательная структура и алгоритм поиска.
5. **MessageBus** — внутренняя реализация очереди и правила доставки.

Этот порядок логичен, потому что каждый следующий компонент опирается на предыдущий. После этого можно будет переходить к реализации, уже не возвращаясь к пересмотру архитектуры.
