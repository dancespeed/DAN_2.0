2. Accepted role of the internal bus

The internal DAN bus follows the simple model:

Sender
   ↓
MessageBus
   ↓
Receiver Module

The delivery service routes a message by Receiver. The receiving module reads the message and executes the required behavior using its own internal code.

There are no runtime Object, ObjectTable, object handlers, or object lifecycles.

3. Accepted meaning of ObjectId

ObjectId is a field of the DAN message protocol.

It identifies the subject, command target, parameter, state, or action inside the receiving module.

Receiver  → which module receives the message
ObjectId  → what the message concerns inside that module
MessageId → what operation or description is carried
Value     → argument or value

ObjectId does not require a separate C++ object.

4. Standardized module protocols

For every functional module type, DAN will define one fixed message standard.

Examples:

DAN PWM Message Standard
DAN Button Message Standard
DAN Temperature Message Standard

All modules implementing the same functional type use the same:

ObjectId values;

MessageId values;

interpretation of Value;

message directions and response rules.

Multiple implementations of the same type differ by ModuleId, while their protocol remains identical.

5. Single source of protocol definitions

The protocol must be described once and shared by senders and receivers.

DAN Protocol Definition
        ├── Logic
        ├── PWM modules
        ├── Button modules
        ├── CAN
        ├── Diagnostics
        └── Configuration tools

A module must include the corresponding standard definition rather than duplicate its own command list.

Illustrative form:

#include <dan/protocol/pwm.hpp>

The exact directory structure and C++ interface have not yet been approved.

6. Documentation rule

The fixed DAN message standards will be documented under docs.

The documentation will define:

general message structure;

common message semantics;

per-module-type command standards;

immutable identifiers;

extension and versioning rules.

Approved identifiers do not change meaning and are not reused.

7. Configuration model

The system configuration remains a scenario consisting of standard DAN messages:

ConfigurationTable
        ↓
MessageBus
        ↓
Modules

Logic and configuration mechanisms form messages using the shared protocol definitions.

The receiving module does not need to know whether a message came from:

ConfigurationTable;

another module;

CAN;

diagnostics;

an external configurator.

8. Message format

The accepted message size is 8 bytes:

Header
ObjectId
Value

Header fields:

Sender
Receiver
MessageType
MessageAttribute
MessageId
